How benchmarking works

01

PROFILING_ENABLE is always enabled on Aether's OpenCL queue; event profiling is required and cannot be switched off.

02

Each rule is executed on the selected OpenCL GPU against the synthetic word corpus, after warm-up iterations. GPU Kernel Time comes from device event START/END timestamps and excludes Python enqueue/driver dispatch overhead.

03

End-to-End Time separately measures host enqueue plus queue completion wait. It is diagnostic; ranking and optimization use GPU Kernel Time.

04

Both dictionary modes process exactly Max words per rule and use the same word-length and character-class profile. Only the input content/repetition changes, so work-item counts are directly comparable.

05

Reports record the selected dictionary mode, exact words-per-rule count, and word-length distribution so benchmark conditions can be compared later.

06

Each visualized rule file also gets a self-contained interactive HTML report. Select a performance tier to inspect exact commands, search the list, and export that entire tier as a separate .rule file.

SELECTION STRATEGY / COVERAGE OPTIMIZATION

Frequency ranking vs. CELF marginal coverage

Both methods rank candidate rules, but they optimize different outcomes: standalone hit count or the number of new TARGET words recovered by the selected set.

RULE BUDGET AWARE
01 SIMPLE BASELINE

Frequency selection

Score each rule independently by its raw GPU hit count, then sort the candidates from highest to lowest.

  • Simple and direct. A one-time ranking is easy to inspect and useful as a fast baseline.
  • Preserves standalone popularity. Rules with high individual hit counts rise to the top.
  • Overlap is not discounted. Several high-ranked rules may recover many of the same TARGET words.
BEST WHEN You want a quick frequency-ordered list or a simple reference ranking.
02 COVERAGE-DRIVEN

CELF greedy selection

Choose the rule that adds the most currently uncovered TARGET words, update the covered set, and repeat.

  • Accounts for overlap. A TARGET word already recovered by an earlier rule adds no new marginal gain.
  • Adapts after every pick. A rule with a lower standalone count can become more valuable when it covers different words.
  • Uses lazy evaluation. Upper bounds narrow the challengers; an exact, duplicate-aware score verifies a winner before it is committed.
BEST WHEN You have a fixed rule budget and want to maximize distinct TARGET-word recovery.
WHY THE DIFFERENCE MATTERS

A rule's value depends on what the selected rules have already covered.

A
Less repeated coverage

Previously recovered TARGET words stop inflating the value of another rule.

B
More complementary picks

Rules that reach different parts of the TARGET set can move ahead of redundant high-frequency rules.

C
Budget tied to new recovery

Each selection is judged by its additional contribution to the union of recovered words.

CELF SELECTION LOOPLazy candidate evaluation with exact winner verification
01Build candidate boundsEstimate which rules may still be competitive.
02Refresh challengersRe-evaluate candidates whose bounds can beat the current winner.
03Verify exact gainCount distinct, still-uncovered TARGET words for the winner.
04Update and repeatCommit the rule, update coverage, and continue within the budget.
↗

Choosing a mode: Frequency remains the default lightweight ordering. Use --select-mode greedy to enable CELF when distinct TARGET coverage is the goal. With the default --select-cost-alpha 0, CELF optimizes pure marginal coverage; a positive alpha adjusts gain by rule depth and favors shorter chains among rules with similar gain.
