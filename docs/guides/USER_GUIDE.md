# RULEOPS — User Guide (CLI and UI)

> [← Documentation index](../README.md) · [Project README](../../README.md)

This guide explains how to use RULEOPS through the Control Center (UI) and from the command line (CLI). UI button and field names are kept exactly as they appear in the interface so they are easy to find.

**Scope of use:** RULEOPS is a collection of tools for authorized password-security research, password-strength audits, and Hashcat rule analysis. Use it only with data and systems you are explicitly authorized to test. Input files may contain confidential information; store and share them in accordance with your organization's policies.

## 1. Choosing the right tool

Each tool handles a different part of a Hashcat-rule workflow. You do not need to run every tool in sequence—choose the tools that fit your task.

| Tool | Purpose | Main input | Typical output |
|---|---|---|---|
| **RULEST** | Generates rule and rule-chain candidates from BASE/TARGET pairs; optionally runs Frequency or CELF selection | BASE wordlist and TARGET wordlist | `.rule` / `.txt` file, optionally files for additional budgets |
| **Rule Ranker** | Scores rules against a wordlist and CRACKED set; can also run CELF or analyze CSV data | Wordlist, rules or CSV, CRACKED list | Ranking CSV, selected rules, analysis report |
| **Concentrator** | Combines, extracts, generates, and filters rule collections | One or more rule files | Extracted, generated, or cleaned ruleset |
| **Rulestripper** | Reconstructs rules/transformation chains that turn BASE words into TARGET words | BASE and TARGET | Rule file |
| **Rule Minimizer** | Removes rules with identical behavior on a test-word set | Rule file, optional test words | Smaller rule file, retaining the first occurrence |
| **Aether** | Measures rule execution time on a GPU and creates performance reports | Rule file or directory | JSON/HTML reports, PNG charts, and optionally an optimized ruleset |
| **Email Rule Extractor** | Derives append-style rules from recurring patterns in email local parts and domains | `.txt` or `.csv` file containing email addresses | Downloadable `.rule` file |
| **Top-N Seed Generator** | Generates rule-seed families independently from the most common patterns in TARGET | TARGET wordlist | `.rule` file |
| **PCFG Corpus Profiler** | Creates an aggregated report of lengths and character classes; does not generate passwords or rules | Wordlist or `COUNT VALUE` file | JSON report |
| **GPU Diagnostics** | Checks PyOpenCL, OpenCL platforms, and devices visible to the current Python environment | Runtime environment | Text and JSON report on stdout |

The Control Center exposes these as separate sections: RULEST, Rule Ranker, Concentrator, Rulestripper, Rule Minimizer, Email Extractor, and Aether. Top-N Seed Injection is part of the RULEST configuration. PCFG Profiler, the standalone Top-N Seed Generator, and GPU Diagnostics are run from the CLI.

### Understanding BASE, TARGET, WORDLIST, and CRACKED

- **BASE** — source words against which the engine tests transformations.
- **TARGET** — target set to which RULEST/Rulestripper match transformations.
- **WORDLIST** in Rule Ranker — the source words to which transformations are applied.
- **CRACKED** in Rule Ranker — target values used to evaluate coverage. This is a separate input from WORDLIST.
- **Rule file** — a text file containing Hashcat rules, usually one rule or command chain per line.

Do not confuse the two CELF implementations:

- **RULEST CELF** evaluates marginal coverage of the **TARGET** set by candidates generated by RULEST and, optionally, imported rules.
- **Rule Ranker CELF** evaluates coverage of the **CRACKED** set by candidates sourced from a ranking CSV or an existing rule file.

For algorithm details, see [RULEST CELF](../engineering/RULEST_CELF.md) and [Rule Ranker CELF](../engineering/CELF_RANKER.md).

## 2. Installing and starting the Control Center

### Requirements

- Python 3.9 or later.
- Packages listed in `requirements.txt`.
- A working driver and OpenCL runtime for GPU features.
- Enough RAM and disk space for the size of your data.

A GPU is not required for every task. For example, Rule Ranker `handler`, PCFG Profiler, and many Minimizer operations run without a GPU. `rank`, GPU CELF, RULEST, and Aether require a working OpenCL environment for their GPU paths.

### Installation

Run these commands from the project directory.

**Linux / macOS**

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

**Windows (PowerShell)**

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

If PowerShell blocks environment activation, you can invoke the interpreter without activating the environment: `.venv\Scripts\python.exe`.

### Starting the UI

**Linux / macOS**

```bash
./start_gui.sh
```

If needed, grant the script execute permission: `chmod +x start_gui.sh`.

**Windows**

```bat
start_gui.bat
```

By default, the launcher listens on `0.0.0.0:8765` to allow access from a trusted local network. Open the local address printed in the terminal, usually `http://127.0.0.1:8765`. On first launch, set an application password of at least 12 characters.

To bind only to the current computer:

```bash
RULEST_HOST=127.0.0.1 ./start_gui.sh
```

On Windows, set the variable before running `start_gui.bat`:

```bat
set RULEST_HOST=127.0.0.1
start_gui.bat
```

You can also start the server without the launcher and specify the host and port:

```bash
python app.py --host 127.0.0.1 --port 8765
```

### Access security

- The built-in server uses **HTTP**, not HTTPS. The application password does not encrypt network traffic.
- Do not expose port `8765` directly to the public Internet or configure router port forwarding for it.
- Restrict access from other devices to a trusted LAN/VPN, or use a correctly configured TLS reverse proxy.
- Protect the project directory, `runs/`, input files, `auth.json`, and `security.sqlite3`.

Additional server protection settings are described in [Security Hardening](../operations/SECURITY_HARDENING.md), and Linux service configuration is described in [systemd Service](../operations/SYSTEMD_SERVICE.md).

## 3. Common UI workflows

### 3.1 Selecting a tool and preparing files

Choose a tool from the left-hand navigation panel. Each panel has its own input fields, settings, job monitor, and results section.

Files can usually be added in one of three ways:

1. Select **Choose a file** / **Add rules file**.
2. Drag a file onto the upload area.
3. Select a previously stored item from the **Or reuse saved…** menu.

After upload, wordlists and rule files are stored in the library and can be reused in later jobs. CSV files specific to a Rule Ranker workflow are temporary files.

### 3.2 Input library

The library stores:

- `runs/library/wordlists/` — BASE, TARGET, WORDLIST, and CRACKED files;
- `runs/library/rules/` — seed files, candidate files, and source rulesets.

Select a saved file from the menu to use it as input for a tool. Tools that accept multiple files (such as Concentrator and Aether) allow you to add several files. Identical files are recognized by content, while files with the same name but different content remain separate variants.

### 3.3 Launching and monitoring jobs

Before starting, check all required inputs and the workflow mode, then use the relevant start button, for example **Launch engine**, **Run ranking**, **Run Concentrator**, **Extract rules**, or **Run benchmark**.

The monitoring cards show, among other things:

- **Engine Status** — job state (for example, idle, running, completed, failed, or stopped);
- **Active Stage** — the engine stage currently running;
- **Elapsed Time** — time since the job started;
- **Output Files** — number of artifacts produced by this run;
- **ETA** — an estimate for the current stage, not a guaranteed completion time for an entire multi-stage job.

The Control Center runs one server-side job at a time. RULEST provides pause/resume and stop controls at safe checkpoints. Other jobs have a cancel button; cancellation interrupts the active process and does not mean that the job can resume from the point where it stopped. Partial output files may be retained depending on the tool and the time of cancellation.

### 3.4 Results and history

Current results appear in the tool's **Output files** section. Download a file from the results list after the job completes.

The **Run storage** page stores the history of server-side tool runs. You can open a saved run, inspect or download its artifacts, download the entire run directory as a ZIP, or delete a specific run directory.

**Note:** **Delete all run folders** is destructive. It removes run-output directories. It does not remove the `runs/library/` library, but it does remove saved results, logs, and partial files in run directories. Download any results you need before deleting them.

### 3.5 Live activity and password

- **Live activity** displays the shared log of current work. You can enable line wrapping, expand the view, export the log, or clear the visible log.
- **Change password** in the top bar lets you change the application password.
- **Completion sound** controls a short sound played in the current browser tab when a job completes successfully.

## 4. RULEST — rule generation

RULEST generates rules and transformation chains that match BASE words to TARGET words. It works in multiple stages; the main search uses the GPU/OpenCL, while Stage 0 is a CPU stage.

### 4.1 RULEST in the UI

#### Step 1 — Input files

In **Input files**, add:

- **Base wordlist** — required BASE file;
- **Target wordlist** — required TARGET file;
- **Custom seed rules** — optional rule file to extend the Stage S seed pool.

You can upload files or select previously saved items from the library.

#### Step 2 — Engine configuration

The main settings are:

| Field | Meaning |
|---|---|
| **Maximum depth** | Maximum rule-chain length, from 1 to 31. Greater depth increases the search space and computational cost. |
| **Target runtime** | Target search duration, in hours. |
| **Maximum chains** | Chain limit; `0` leaves the engine's default behavior unchanged. |
| **RNG seed** | Optional random-generator seed. Helps reproduce a run with the same data and settings. |
| **Bloom filter size** | Bloom-filter size; `0` lets the engine choose a GPU size automatically. |
| **GPU device** | Empty = automatic selection. You can specify an index, part of a device name, `all`, or a list of indices such as `0,1`. |
| **Disable Bloom sharding** | Forces a single Bloom-filter shard; normally leave this disabled. |
| **Allow reject rules** | Allows rules that intentionally reject candidates; enable only when you explicitly need this behavior. |
| **Disable built-in seeds** | Disables the built-in Stage S seed families. |
| **Functional rule minimization** | Enables/disables final removal of rules with equivalent signatures on the probe set. Enabled by default. |

Use **Detect GPUs** to refresh the device list. A detailed diagnostic report is available in the GPU status section.

#### Step 3 — Optional stages

**Stage 0 · Token Strip** — enable **Enable Stage 0** to run the CPU stage that detects stem and insertion patterns. Parameters include minimum stem length, maximum prefix/suffix length, leet-ambiguity threshold, worker count, chunk size, and Bloom-filter memory for BASE membership checks.

**Top-N Seed Injection** — runs in memory during a RULEST run. When enabled, the engine analyzes the first `Top-N passwords` TARGET entries (`0` in the CLI means scan the entire file), generates a bounded seed pool, and injects it into later stages. Available settings include:

- **Complementary mode** — favors patterns emitted less often by Stage 0;
- **Adaptive family budgets** — distributes the seed-family budget based on pattern frequency in TARGET;
- **Top-N passwords**, **Max seeds**, and **Inject cap** — limits for input scanning, seed generation, and chains injected into later stages;
- **PCFG corpus profile** — optional aggregated JSON profile that influences family budgets. It does not pass specific passwords to RULEST.

**Genetic algorithm (Stage 3)** — enable this for additional evolutionary chain search. Parameters are `Generations`, `Population size`, and `Elite ratio`. Requires `Maximum depth ≥ 2`.

#### Step 4 — Rule selection

- **Frequency** — by default, sorts output by raw GPU hit count.
- **Greedy** — uses lazy-greedy/CELF selection based on exact marginal TARGET coverage. At each step, it selects the rule that adds the most new covered items.
- **Selection budget** — maximum number of selected rules; `0` in Greedy mode means continue until the candidate pool is saturated.
- **Additional budget sweep** — comma-separated budgets; one CELF run can produce several files of different sizes.
- **Cost alpha** — increasing this value favors shorter chains when coverage gains are similar.
- **Output format** — `Compact · Hashcat line` preserves concatenated operators (default); `Expanded · spaced operators` separates every operator and its arguments with spaces, using the same readable layout as Concentrator's Expanded mode. The expanded layout is intended for inspection and RULEOPS workflows; choose Compact when a downstream tool requires standard compact rule lines.
- **CELF cost profile** — optional PCFG profile used to cost-weight literal characters in Greedy mode.
- **Report exact recovery** — adds a report with the exact number of distinct TARGET items recovered by the selected rules. It does not run a second exact-scoring phase.

#### Step 5 — Custom seed directly into CELF

**Inject custom seed file into CELF** is different from regular **Custom seed rules**:

- regular `Custom seed rules` feeds the Stage S seed path;
- CELF import adds rules directly to the Greedy/CELF selection candidate pool.

To use CELF import:

1. Upload a file through **Custom seed rules** or select a previously saved rule file.
2. Set **Selection mode** to **Greedy**.
3. Enable **Inject custom seed file into CELF**.
4. Enter a positive number in **Maximum imported CELF rules**. The default is 1000; there is no fixed upper limit.
5. Run RULEST.

Each rule is validated, filtered against the maximum-depth limit, deduplicated, and exactly scored. An imported rule is a candidate—it is **not selected automatically**. See [RULEST CELF seed files](RULEST_CELF_SEEDS.md) for details. The run log reports whether the optional import is disabled or enabled, the validation counts (including zero accepted rules), and the number of external candidates actually added to CELF.

### 4.2 RULEST in the CLI

Basic syntax:

```bash
python run_rulest.py BASE.txt TARGET.txt --output candidates.rule
```

To write the same operator-spaced layout as Concentrator's Expanded mode:

```bash
python run_rulest.py BASE.txt TARGET.txt --output candidates-expanded.rule --output-format expanded
```

The default `line` format keeps each rule compact. `expanded` inserts spaces between individual operator+argument tokens in every output rule, including custom CELF candidates that make it into the selected output.

Example with greater depth, a longer budget, and a deterministic seed:

```bash
python run_rulest.py BASE.txt TARGET.txt \
  --output candidates.rule \
  --max-depth 3 \
  --target-hours 1.0 \
  --seed 42
```

Example enabling Stage 0 and the genetic algorithm:

```bash
python run_rulest.py BASE.txt TARGET.txt \
  --token-strip \
  --genetic --genetic-generations 50 --genetic-pop 200 --genetic-elite 0.15 \
  --max-depth 3 \
  --output generated.rule
```

Example of Greedy selection with an external CELF rule file:

```bash
python run_rulest.py BASE.txt TARGET.txt \
  --select-mode greedy \
  --select-budget 5000 \
  --celf-seed-rules curated.rule \
  --celf-seed-max-rules 2500 \
  --output selected.rule
```

You can repeat `--celf-seed-rules PATH` to add multiple files. The `--celf-seed-max-rules` limit is shared across all specified files. The value must be a positive integer. This option requires `--select-mode greedy`.

The difference between the two seed inputs:

```bash
# The file feeds the Stage S seed path
python run_rulest.py BASE.txt TARGET.txt --seed-rules seeds.rule

# The file provides additional CELF candidates (requires greedy)
python run_rulest.py BASE.txt TARGET.txt -M greedy --celf-seed-rules curated.rule
```

Common CLI options:

| Option | Meaning |
|---|---|
| `-o`, `--output` | Output filename. |
| `-d`, `--device` | GPU: index, name, `all`, or a list of indices. |
| `-L`, `--list-devices` | Lists detected devices and exits. |
| `-m`, `--max-depth` | Maximum chain depth, 1–31. |
| `-t`, `--target-hours` | Target search duration in hours. |
| `-c`, `--max-chains` | Chain limit; `0` = default behavior. |
| `-B`, `--bloom-mb` | Bloom-filter memory in MB; `0` = automatic. |
| `-r`, `--seed-rules` | Stage S seed file. |
| `-n`, `--no-builtin-seeds` | Disables built-in seed families. |
| `--no-minimize` | Skips final signature minimization. |
| `--token-strip` | Enables Stage 0; parameters: `--token-strip-min-stem`, `--token-strip-max-prefix`, `--token-strip-max-suffix`, `--token-strip-min-leet-amb`, `--token-strip-workers`, `--token-strip-chunk-size`, `--token-strip-bloom-mb`. |
| `--topn-seeds` | Enables Top-N Seed Injection. Options: `--topn-n`, `--topn-max-seeds`, `--topn-complementary`, `--topn-no-adaptive-budget`, `--topn-profile`, `--topn-inject-cap`. |
| `-g`, `--genetic` | Enables Stage 3; `-G`, `-P`, and `-E` set generations, population, and elite ratio. |
| `-M`, `--select-mode` | `frequency` or `greedy`. |
| `-b`, `--select-budget` | Number of rules in Greedy output; `0` = until saturation. |
| `-s`, `--select-budgets` | Additional output thresholds, comma-separated. |
| `-a`, `--select-cost-alpha` | Weight for rule-chain length cost. |
| `--select-cost-profile` | Aggregated PCFG profile for CELF cost weighting. |
| `--celf-seed-rules`, `--celf-seed-max-rules` | External CELF candidates and their import limit. |
| `--output-format line / expanded` | Compact output (default) or operator-spaced expanded output. |
| `-e`, `--exact-recovery` | Adds an exact TARGET recovery report. |
| `-S`, `--seed` | Random seed for reproducibility. |
| `-D`, `--debug` | Verbose logging. |
| `-p`, `--profile` | Profiles stages and GPU CELF metrics. |

`--depth2-chains` through `--depth10-chains` let you override limits for individual depths. The full option list is available with:

```bash
python run_rulest.py --help
```

## 5. Rule Ranker — evaluation and optimization

Rule Ranker has three workflows. In the UI, switch between the **Rank rules**, **Optimize ruleset**, and **Analyze CSV** tabs. In the CLI, choose the `rank`, `postprocess`, or `handler` subcommand.

### 5.1 Rank rules — GPU ranking

**UI inputs:**

- **Base wordlist**;
- **Cracked-password list**;
- **Candidate ruleset**.

First add the two shared input files, then add the rule file in the Rank rules tab.

**Main UI settings:**

- **Ranking CSV output** — name of the primary CSV output.
- **Top rules to export** — number of top rules to write to an additional `.rule` file; `0` disables this additional export.
- **GPU memory preset** — `Recommend`, `Low memory`, `Medium memory`, or `High memory`.
- **Words per GPU batch**, **Global hash-map bits**, **Cracked hash-map bits** — manual buffer/map-size overrides; leave them empty to use automatic sizing/the preset.
- **Adaptive MAB** — the default method: multi-pass sampling and elimination of weaker candidates.
- **Legacy exhaustive** — the older exhaustive-ranking method.

MAB parameters: `Exploration factor`, `Screening trials`, `Final trials`, `Sample words / trial`, `OpenCL device ID`, and `Zero-success elimination`. More trials increase computational cost but can improve ranking stability.

**CLI:**

```bash
python run_ranker.py rank \
  --wordlist wordlist.txt \
  --rules candidates.rule \
  --cracked cracked.txt \
  --output ranking.csv \
  --topk 1000 \
  --preset recommend
```

Legacy mode:

```bash
python run_ranker.py rank --legacy \
  -w wordlist.txt -r candidates.rule -c cracked.txt \
  -o ranking_legacy.csv
```

List devices and view all options:

```bash
python run_ranker.py rank --list-devices
python run_ranker.py rank --help
```

### 5.2 Optimize ruleset — GPU CELF

This workflow optimizes an existing candidate set. You need the shared **Base wordlist** and **Cracked-password list** inputs. Select one candidate source:

- **Plain .rule file** — a rule file;
- **Ranking CSV** — output from the earlier Rank rules workflow.

Main settings:

| Field | Meaning |
|---|---|
| **Candidate limit** | Number of top-ranked candidates passed to CELF; default is 20,000. |
| **Selection budget** | Maximum number of rules in the final ruleset. `0` means select until the candidate pool is saturated. |
| **Budget sweep** | Several export thresholds from one Greedy ordering, for example `64,250,5000`. |
| **Rule batch size** | Candidates evaluated in a single GPU dispatch. |
| **Words per GPU batch** | Number of words processed in a GPU batch. |
| **Maximum word length** | Longer input words are skipped. |
| **Maximum rule length** | Upper limit for rule text length. |
| **Maximum output length** | Buffer size for transformed output; it must be at least as large as the word limit unless automatic sizing is enabled. |
| **Cost alpha** | Rule-cost weight; `0` means pure marginal coverage. |
| **Enable GPU profiling** | Adds timing measurements for individual phases and OpenCL events, with a small overhead. |

**Automatically size maximum output length** estimates the worst-case output length of a rule before scoring. **Print output-length estimate only** performs the estimate and exits without starting GPU work.

CLI example using a CSV source:

```bash
python run_ranker.py postprocess \
  --ranking-csv ranking.csv \
  --wordlist wordlist.txt \
  --cracked cracked.txt \
  --output optimized.rule \
  --candidates 20000 \
  --budget 5000
```

Example using a `.rule` source and multiple budgets:

```bash
python run_ranker.py postprocess \
  --rules-file candidates.rule \
  --wordlist wordlist.txt \
  --cracked cracked.txt \
  --output optimized.rule \
  --candidates 20000 \
  --budgets 64,250,5000
```

Exactly one source is required per invocation: `--ranking-csv` or `--rules-file`. See `python run_ranker.py postprocess --help` for the other options.

Rule Ranker CELF uses exact GPU recompute scoring and CPU-side selection coordination; do not confuse it with the RULEST CELF implementation.

### 5.3 Analyze CSV — analysis without a GPU

This workflow reads ranking results from a CSV/TXT file and can:

- generate a summary report;
- write cleaned Hashcat rules to a `.rule` file;
- optionally write rules together with results/scores;
- limit the export to the first `Top rules` entries.

In the UI, add **Ranking data**, set the output names, and choose the required switches. `Skip statistics` reduces RAM use but skips per-rule statistics and the summary report. `Rules only` writes only cleaned rules. `Parallel file processing` is useful when processing multiple input files.

**CLI:**

```bash
python run_ranker.py handler \
  --input ranking.csv \
  --output summary.txt \
  --rules-output clean_rules.rule \
  --top 5000
```

Analyze multiple files:

```bash
python run_ranker.py handler -i rank_a.csv rank_b.csv \
  -o combined_summary.txt --parallel
```

RAM-saving mode, rules only:

```bash
python run_ranker.py handler -i ranking.csv \
  --rules-output clean_rules.rule --rules-only --no-stats
```

Full option list: `python run_ranker.py handler --help`.

## 6. Concentrator — collecting and cleaning rules

Concentrator works with one or more rule files or directories containing rule files. In the UI, select **Rule source files**, then choose one of four modes.

### 6.1 Extract

Aggregates input files, counts occurrences, and exports a specified number of unique rules.

- **Top rules to extract** — maximum number of output rules.
- **Ranking strategy: Frequency** — sorts by frequency.
- **Statistical · Markov** — sorts using a statistical token model.

### 6.2 Combinatorial

Generates combinations of rule units/tokens from the input collection.

- **Target rules** — target number of generated rules.
- **Minimum / Maximum token length** — length range for combinations.

The target count is a generation goal; the actual output depends on validity, available combinations, and filters.

### 6.3 Markov

Generates statistically likely rule chains using a Markov/Kneser–Ney model and a synthetic corpus targeted at the input patterns.

- **Target rules** — target number of rules.
- **Minimum / Maximum token length** — rule-chain length range.

### 6.4 Process & clean

Processes an existing ruleset. Filters are applied in a fixed order:

1. **Minimum occurrence** — keeps rules that occur at least N times.
2. **Maximum rules** — limits the output to the top N ranked rules.
3. **Functional minimization** — removes rules with equivalent behavior; may require substantial RAM.
4. **Inverse cutoff** — keeps rules ranked below the specified threshold.
5. **Hashcat cleanup** — validates syntax in CPU or GPU mode.

If no cleanup filter is selected in the CLI, `-p` opens the interactive processing menu. In the UI, select filters in the form.

### 6.5 Global settings

- **Output base name** — output filename prefix; the selected mode adds a suffix.
- **Maximum input rule length** — longer input lines are skipped.
- **Output format** — `line` (standard representation) or `expanded` (expanded tokens).
- **Enable OpenCL acceleration** — uses available OpenCL for validation/generation; disable it to force the CPU path.
- **In-memory processing** — keeps data in RAM. When disabled, the UI uses disk-based processing.
- **Confirm high-memory operations** — explicitly allows selected high-memory operations when the system reports high memory pressure.

### 6.6 CLI

The syntax requires paths to files/directories and one operating mode.

```bash
# Extract the 5,000 most frequent rules
python concentrator.py -e -t 5000 rules/*.rule

# Extract using statistical ranking
python concentrator.py -e -t 5000 -s rules/

# Generate combinations with 2–4 tokens
python concentrator.py -g -n 50000 -l 2 4 rules/

# Generate Markov rules
python concentrator.py -gm -gt 10000 -ml 1 3 rules/

# Process with non-interactive filters
python concentrator.py -p --filter-min-occ 2 \
  --filter-max-rules 20000 --filter-hashcat-cleanup cpu rules/
```

In Process & clean mode, add functional minimization with `--filter-func-redundancy`; this operation can be memory-intensive. `--filter-inverse N` enables the inverse ranking cutoff.

Common CLI options: `-ob/--output_base_name`, `-f/--output-format`, `-m/--max_length`, `--temp-dir`, `--in-memory`, `-d` (disk mode), and `--no-gpu`. `-y/--yes` automatically confirms high-resource operations—use it only when you understand their resource requirements.

Running without arguments opens Concentrator's interactive mode:

```bash
python concentrator.py
```

Full option list: `python concentrator.py --help`.

## 7. Rulestripper — extracting rule chains

Rulestripper attempts to decompose TARGET words into BASE words and the Hashcat transformations that connect them. It is a multiprocessing CPU tool with shared memory; do not confuse it with RULEST's GPU search.

### 7.1 Rulestripper in the UI

Add a **BASE wordlist** and a **TARGET wordlist**. BASE is normalized to lowercase, as described by the UI field.

Settings:

| Field | Meaning |
|---|---|
| **Maximum chain depth** | `0` means the maximum Hashcat depth (31); a positive value limits chain length. |
| **Minimum stem length** | Minimum length of the base stem; default is 4. |
| **Leet ambiguity** | Limit for ambiguous leet positions; default is 3. |
| **Worker processes** | `0` = automatic process count. |
| **Words per task** | `0` = automatic chunk size. |
| **ASCII offset range** | Range of ASCII offsets for the relevant extraction mode. |
| **Toggle-chain seed rules** | Adds common T-position and leet chains; enabled by default. |
| **Enhanced extraction modes** | Enables additional modes (including insert, swap, range, and Hashcat 8 operators); enabled by default. |
| **Debug output** | Additional diagnostic messages. |

When the job completes, download the output `.rule` file from the results panel.

### 7.2 CLI

```bash
python run_rulestripper.py BASE.txt TARGET.txt \
  --output extracted.rule \
  --max-depth 2 \
  --min-stem 4 \
  --workers 8
```

Useful options:

- `--max-depth N` — `0` = 31;
- `--min-stem N` — default is 4;
- `--leet-amb N` — default is 3;
- `--no-toggle-seeds` — disables toggle-chain seeds;
- `--no-new-modes` — disables enhanced extraction modes;
- `--ascii-range N` — default is 3;
- `--workers N` — `0` = CPU count;
- `--chunk-size N` — `0` = automatic;
- `--debug` — diagnostic mode;
- `--no-color` — disables terminal color codes.

Full option list: `python run_rulestripper.py --help`.

## 8. Rule Minimizer — reducing equivalent rules

Rule Minimizer compares rule signatures: for each rule, it computes transformation results on a set of test words. If two rules produce the same set of results for all probe words, it keeps the earlier rule in the file and removes the later one. This preserves the original ordering/ranking.

**Important limitation:** identical signatures on a finite probe set are not formal proof of equivalence for every possible word. For unusual datasets, add representative probe words or a probe file.

### 8.1 UI

1. Add **Input rules** or select a file from the library.
2. Optionally add an **Extra probe wordlist**.
3. Set **Probe words from file**, **Worker processes**, and **Random seed**.
4. You can enter **Additional probe words**, separated by spaces.
5. Enable **Multibyte / Unicode mode** if rules should be analyzed on UTF-8 byte sequences, including Polish and other non-ASCII characters.
6. Set the output name and select **Minimize rules**.

### 8.2 CLI

```bash
python minimizer.py candidates.rule --output minimized.rule
```

Additional probe words:

```bash
python minimizer.py candidates.rule -o minimized.rule \
  --extra-probes password admin letmein
```

Probe words sampled from a file:

```bash
python minimizer.py candidates.rule -o minimized.rule \
  --probe-file audit_words.txt --probe-words 200 --seed 42
```

UTF-8 byte mode:

```bash
python minimizer.py candidates.rule -o minimized_utf8.rule --multibyte
```

Useful options:

- `--list-probes` — displays the built-in probe set and exits;
- `--probe-file FILE` and `--probe-words N` — sample additional words from a file;
- `--seed N` — repeatable sampling of the probe file;
- `--workers N` — `0` = automatic process count; default is 1;
- `--debug` — displays retained/removed rules and their duplicates;
- `--debug-rule RULE` — traces one rule;
- `--debug-file FILE` — traces every rule in a file.

Full option list: `python minimizer.py --help`.

## 9. Aether — GPU performance benchmarking

Aether measures rule execution time on an OpenCL GPU and creates comparative reports. It does not evaluate TARGET/CRACKED coverage. It uses a synthetic test corpus with a controlled number of work-items and a controlled profile of lengths/character classes.

For the exact timing methodology, metric formulas, validation categories, report fields and interpretation caveats, see [Aether GPU Benchmarking](../engineering/AETHER_BENCHMARKING.md).

### 9.1 UI

Add between 1 and 12 rule files. Each file is validated before benchmarking; the tool reports invalid syntax, CLI-only operators, and valid commands that the current OpenCL interpreter does not support separately. Only rules supported by the benchmark are measured.

Settings:

| Field | Meaning |
|---|---|
| **Iterations** | Number of test iterations per rule. |
| **Test runs** | Number of measurement repetitions for statistical stability. |
| **Max words** | Exact number of GPU work-items per rule. |
| **Max test rules** | Limit on the number of rules tested in each file. |
| **Chart DPI** | Resolution of generated PNG charts. |
| **GPU platform/device index** | OpenCL platform and device indices. |
| **Visualize** | Generates PNGs and a standalone interactive HTML report; enabled by default in the UI. |
| **Repeat identical dictionary** | Repeats the same 16-word seed set. When unchecked, variants with the same length and character-class profile are generated. Both modes execute exactly `Max words` work-items. |
| **Optimize search** | Selects the fastest measured rules within a cumulative GPU-time budget; it does not preserve target coverage or functional equivalence. |
| **Max rules to optimize** | Limit on the number of rules in the search result/default export from the HTML report. |
| **Max optimize time (µs)** | Cumulative GPU-kernel time budget in microseconds. `30 000 000 µs` corresponds to 30 seconds. |

OpenCL event profiling is always enabled because GPU event timestamps are used to calculate **GPU Kernel Time**. **End-to-End Time** is a separate diagnostic measurement that includes host-side dispatch/wait time. For performance comparisons, primarily use GPU Kernel Time and identical test settings.

After launch, find the results in **Benchmark gallery**. The HTML report lets you browse Fastest / Middle / Slowest categories, search rules, inspect commands, and export a category or a specified number of the fastest rules.

### 9.2 CLI

```bash
python aether.py --rules candidates.rule \
  --output benchmark_results \
  --visualize \
  --iterations 50 \
  --test-runs 3 \
  --max-words 1000
```

Multiple input files:

```bash
python aether.py --rules set_a.rule set_b.rule \
  --output benchmark_results --visualize
```

Optional optimization:

```bash
python aether.py --rules candidates.rule \
  --output benchmark_results --visualize \
  --optimize --max-optimize-rules 500 --max-time 30
```

`--max-time` in the CLI is specified in seconds. The corresponding UI field is in microseconds. Other important options include `--iterations`, `--test-runs`, `--max-words`, `--max-test-rules`, `--dpi`, `--visualization-output`, `--platform`, `--device`, and `--identical-dicts`.

Aether requires a working OpenCL environment. If the `pyopencl` module or runtime is unavailable, the benchmark job will not start. Full option list: `python aether.py --help`.

## 10. Email Rule Extractor — rules from email-address patterns

Email Rule Extractor is a **browser-based tool**. Processing takes place in the browser; there is no separate CLI command, and the output file is downloaded directly.

### Supported input

Upload a `.txt` or `.csv` file containing one address per line. Supported formats are:

- an email address by itself;
- a line in `hash:email` format—the tool scans colon-separated segments from the end and uses the last segment containing `@`.

Domain validation is basic: the domain must contain a dot and be at least 3 characters long.

### Procedure

1. Select **Email Extractor** in the sidebar.
2. Upload a file or drag it onto the **Upload Email List** area.
3. Review the detected domains. You can search for a domain, select/deselect groups, or leave **All domains** selected.
4. **Extract trailing digit patterns only** is enabled by default. In this mode, only usernames ending in digits are included, and the pattern contains those trailing digits and the domain. Disable the option to analyze the full local part together with the domain.
5. Click **Extract Rules**.
6. Review the patterns, occurrence counts, and examples in the results.
7. Click **Download .rule file**.

The output is sorted by pattern frequency, descending. For each character in a pattern, the generator creates a `$` append operator with that character. This is pattern extraction, not a ranking of rule effectiveness against a wordlist.

**Privacy:** because processing runs in the browser, this page does not send the list to the server-side job runner. However, the file may contain personal data—do not share it with unauthorized people.

## 11. Supporting CLI tools: Top-N, PCFG, and GPU Diagnostics

These tools do not have separate entries in the main Control Center menu. Top-N Seed Injection is also embedded in the RULEST configuration.

### 11.1 Top-N Seed Generator

The generator analyzes a selected number of TARGET entries, detects common affix/year patterns, and combines them with a bounded set of transformations. It generates a `.rule` file independently of a RULEST run.

```bash
python run_topn_seedgen.py TARGET.txt \
  --output topn_seeds.rule \
  --top-n 400000 \
  --max-seeds 150000 \
  --complementary
```

Optional PCFG profile:

```bash
python run_topn_seedgen.py TARGET.txt \
  -o topn_seeds.rule \
  --pcfg-profile reports/target_profile.json
```

Options:

- `-n/--top-n` — number of TARGET entries to analyze; `0` or a negative value scans the entire file;
- `-m/--max-seeds` — maximum size of the generated pool;
- `--complementary` — biases the pool toward families less covered by Stage 0;
- `--no-adaptive-budget` — disables adaptive family-budget allocation;
- `--encoding` — input encoding;
- `-w/--workers` — number of CPU workers;
- `--pcfg-profile` — optional JSON file with schema `ruleops.pcfg-profile.v1`.

Full option list: `python run_topn_seedgen.py --help`.

### 11.2 PCFG Corpus Profiler

The profiler creates an aggregate report of corpus length and character composition. The report does not store or print raw values, passwords, substrings, prefixes, suffixes, or rule proposals.

```bash
python run_pcfg_profile.py TARGET.txt \
  --output reports/target-profile.json
```

Compare with an earlier profile:

```bash
python run_pcfg_profile.py MEDIUM.txt \
  --compare reports/small-profile.json \
  --output reports/medium-profile.json
```

You can specify the input format explicitly:

```bash
# Each non-empty line is a value; do not parse a leading count.
python run_pcfg_profile.py TARGET.txt --input-format plain -o profile.json

# Each line has the form COUNT VALUE.
python run_pcfg_profile.py COUNTS.txt --input-format count-value -o weighted.json
```

`auto` (the default) preserves the existing detection of lines beginning with a number followed by a space/tab. `plain` always treats the entire line as a value. `count-value` requires a COUNT prefix; malformed records are reported and skipped.

The report can be used as an optional source of priors for Top-N (`--pcfg-profile` / UI) or as a cost profile for RULEST CELF (`--select-cost-profile`). It is not full PCFG grammar training and is not a password generator.

Full option list: `python run_pcfg_profile.py --help`. Details of the JSON fields are in [PCFG Profile](PCFG_PROFILE.md).

### 11.3 GPU Diagnostics

Run this with the same Python interpreter used to start the Control Center:

```bash
python gpu_diagnostics.py
```

The report shows the Python version, PyOpenCL availability, detected OpenCL platforms and devices, and the availability of system tools such as `clinfo`, `nvidia-smi`, and `rocminfo`. The exit code is `0` when a GPU is detected and `2` when a GPU is unavailable.

If PyOpenCL is not installed, install the dependency into the exact Python environment that runs the UI. If PyOpenCL is available but OpenCL reports no platforms, you need the appropriate GPU vendor driver/runtime—installing the Python package alone does not install a driver.

## 12. File library, run history, and logs

### 12.1 Run storage

Open **Run storage** in the System section. It contains:

- a list of previous runs grouped by tool and input ruleset/wordlist;
- run details and the list of saved artifacts;
- preview and download of individual files;
- download of all artifacts from a specific run as a ZIP;
- deletion of a single run directory.

Aether may store results for multiple rule files in one run folder. Gallery details are grouped by file, while ZIP/download and delete actions apply to the entire run.

### 12.2 Storage Intelligence and cleanup

The Storage Intelligence panel shows RULEOPS data usage, physical disk usage, the application quota, category breakdowns, recently added items, and the largest files.

Available scans/actions:

- **Scan run folders** — identifies empty/log-only directories and repeated runs on the same normalized input data;
- **Scan library + work duplicates** — searches for duplicates between the library and working directories;
- **Delete selected library files** — removes selected library items;
- **Delete all run folders** — removes run directories.

Treat scan results as suggestions to review. Two runs on the same data may have different parameters or results. Check the details before deleting anything, and download any results you need.

The default RULEOPS data limit is 50 GiB and includes run outputs, library files, and temporary uploads. This is an application limit, independent of physical disk capacity. Configuration is described in [Security Hardening](../operations/SECURITY_HARDENING.md).

### 12.3 Live activity

Use **Export log** to save a text log of the current run. **Clear log** clears the visible/centralized log and the `engine.log` record; it is not the same as deleting the entire run directory and its outputs.

## 13. Example workflows

The scenarios below show how tools can be combined. The order is illustrative—not every project needs every stage.

### 13.1 From a BASE/TARGET pair to a compact ruleset

1. Run RULEST or Rulestripper on an authorized BASE/TARGET pair.
2. Save the generated `.rule` file.
3. Optionally use Concentrator to combine collections, select top rules, and clean up syntax.
4. Run Rule Ranker on the candidate file and the appropriate WORDLIST/CRACKED evaluation data.
5. Use **Optimize ruleset** (CELF) to select a smaller subset based on marginal CRACKED coverage.
6. Run Rule Minimizer as an additional signature-reduction step.
7. Use Aether if you want to independently examine the GPU performance of the remaining rules.

### 13.2 A manually curated rule library for RULEST CELF

1. Prepare a small, manually reviewed Hashcat `.rule` file.
2. Upload it to RULEST as **Custom seed rules**.
3. Enable **Greedy** and **Inject custom seed file into CELF**.
4. Set an import limit appropriate for the size of the library.
5. Run selection and check the log for validation/import statistics and the output file.

Rules from the file are candidates; exact CELF determines which ones actually improve TARGET coverage.

### 13.3 Comparing corpus profiles and Top-N settings

1. Run PCFG Profiler on an authorized corpus and save the JSON report.
2. Run Top-N Seed Generator with that profile, or attach the profile in the RULEST Top-N panel.
3. Compare results only on a consistent dataset and with documented parameters.

The PCFG profile describes aggregates of lengths and character classes; it should not be interpreted as a list of specific candidates.

### 13.4 Benchmarking rule speed

1. Upload one or more `.rule` files to Aether.
2. Use identical `Max words`, iterations, repetitions, and dictionary mode for the sets you are comparing.
3. Run the benchmark with Visualize enabled.
4. Compare **GPU Kernel Time** under the same conditions; do not treat `End-to-End Time` as a direct measure of kernel execution time.
5. Use the HTML report to export a selected tier or a specified number of the fastest rules.

## 14. Troubleshooting

### The UI does not open

- Check whether `app.py` is running and whether port 8765 is already in use.
- Open the address printed by the server; on the same computer, try `http://127.0.0.1:8765`.
- If you are connecting from another device, check the LAN address, system firewall, and `RULEST_HOST` setting.

### PyOpenCL is unavailable or no OpenCL platforms are detected

- Run `python gpu_diagnostics.py` with the same Python interpreter used by the UI.
- Missing PyOpenCL indicates a package issue in the Python environment.
- PyOpenCL without detected platforms usually indicates a missing or faulty GPU vendor OpenCL driver/runtime.
- Installing PyOpenCL alone does not install the GPU driver.

### RULEST does not accept CELF import

- Check that **Greedy** is selected (CLI: `--select-mode greedy`).
- Make sure a Custom seed rules file has been selected.
- `Maximum imported CELF rules` / `--celf-seed-max-rules` must be a positive integer.
- Rules outside the supported range, over the depth limit, invalid rules, or duplicates may be skipped.
- CELF import does not replace `--seed-rules` for Stage S.

### Rule Ranker Analyze works, but Rank/Optimize does not

`Analyze CSV` is a CPU workflow. `Rank rules` and GPU coverage in `Optimize ruleset` require working OpenCL. Check the driver, platform, and device index.

### Aether rejects some rule lines

Check the validation report and its line numbers. Aether distinguishes syntactically invalid rules, CLI-only operators, and valid commands unsupported by the current benchmark interpreter. Only explicitly supported rules can be measured.

### Minimizer removes or keeps more rules than expected

The result depends on the probe set. Use `--list-probes`, add representative extra probes or a probe file, set `--multibyte` for Unicode data, and preserve the input result before minimization. Signatures are compared on a finite test set.

### No output file is produced, or the result is empty

- Check that the job ended with status `completed`, not `failed` or `stopped`.
- Read the end of **Live activity**.
- Check whether input files were empty, incorrectly formatted, or filtered out.
- Use **Run storage** to see whether partial artifacts were retained.

### Disk space is running low

Check Storage Intelligence, the largest files, and the 50 GiB limit. Before increasing the limit, verify physical disk capacity and your retention policy. Do not delete run folders without checking whether they contain the only copy of results you need.
